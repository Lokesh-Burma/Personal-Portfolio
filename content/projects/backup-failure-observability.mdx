# Backup Failure Classification & Observability

Backup systems fail in different ways. Some failures are temporary and should be retried. Some are permanent and need clear customer visibility. Some are platform issues that support and engineering need to diagnose quickly.

This project improved how backup failures are classified, stored, and explained, especially across temporary, permanent, and customer-action-needed states.

## Problem

Customers saw storage discrepancies when dashboard values did not match their expected backup size.

Internally, transient failures could keep retrying and increase storage-related counts, but there was not enough visibility into:

- Which items were still retrying.
- Which items had permanently failed.
- Which failures needed customer action.
- Which errors mapped to known categories.
- What happened across retry attempts.

## Goal

The goal was to classify items into clearer states and make the system easier to debug for customers, support, and engineering.

The classification needed to cover:

- Temporary failures that should retry.
- Permanently failed items.
- Customer-action-needed failures.
- Backup errors.
- Restore errors.
- Export errors.
- Post-processing failures.

## Retry History

The system needed attempt-level context.

I added history tracking for retry and restore flows that stored JSON details such as:

- Status.
- Error.
- Error code.
- Data size.

This made it easier to understand what happened before a retry eventually succeeded or failed.

## Classification Model

The classification model introduced clearer categories:

- Temporary failures that are still retryable.
- Permanent failures that should not keep retrying.
- Customer-action-needed failures that require clearer visibility.
- Backup-error items that need distinct handling.

The implementation also preserved previous error information when a retry later succeeded, so earlier failure context was not lost.

## Error-Code Coverage

The initiative expanded error-code coverage from 350 to 2,957 codes.

That mattered because classification quality depends on error-code quality. If the system does not have enough structured error coverage, support visibility and customer-facing diagnostics stay vague.

## Production Rollout

The feature reached canary rollout in February 2026.

One rollout challenge came from a conflicting feature branch, which required creating a new production branch and selectively cherry-picking the intended changes.

## Impact

- Reduced customer confusion around backup storage discrepancies.
- Improved support visibility into retrying and permanently failed items.
- Standardized failure status models across key services.
- Added attempt-level retry history for better diagnostics.
- Expanded error-code coverage from 350 to 2,957 codes.

## Lessons Learned

- Reliability work is not only about reducing failures. It is also about explaining failures clearly.
- Status names must be consistent across services.
- Retry success should not erase useful failure history.
- Error taxonomy quality directly affects support efficiency.
- Canary rollout planning matters when multiple features touch related production areas.
